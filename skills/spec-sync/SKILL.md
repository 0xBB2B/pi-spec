# spec-sync：规范与代码对账

需求流程的门禁只覆盖走流程的改动；极小改动与手改代码会让 `.pi-spec/spec/` 漂移。本 skill 找出漂移并交用户裁决。所有确认动作使用 `ask_user_question`。

## 范围与前置

- `/spec-sync` 不带参数对 `spec/` 下全部规则文件；带域名只对该域子目录。
- 存在 `status` 不为 `accepted` 的需求目录时，先告知用户"进行中需求会造成暂时不一致"，由用户选择继续或先完成该需求。
- 报告与临时物写入 `.pi-spec/.cache/sync/`。

## 第一步：静态检查

对每个规则文件跑 spec-docs 的 `lint.sh --spec <文件>`，并核对 INDEX.md 与目录一一对应。违规项直接进入第三步的裁决清单。

## 第二步：双向对账

按域串行执行（验收例子可能改变系统状态，禁止并发）：

1. **规范 → 代码**：直接调用 acceptance-reviewer，规则文件路径清单为该域全部规则文件，报告路径 `.pi-spec/.cache/sync/<域>.acceptance.md`，启动方式同正常验收。FAIL 与未覆盖项即"规范有、代码不符"。
2. **代码 → 规范**：派 Explore（breadth: very thorough），任务只有一句：列出仓库对外暴露的全部入口——命令行子命令与参数、HTTP 路由、界面页面与可操作元素——只报清单不解释实现。与该域规则文件的逻辑、约束与验收中出现的命令、路径和界面元素比对，规范未记录的入口即"代码有、规范没有"。

## 第三步：裁决

把全部不一致项汇总成一张表（来源 / 规则或入口原文 / 实际观察），逐条请用户裁决，选项固定两个：

| 裁决 | 处理 |
|---|---|
| 以代码为准，改规范 | 主 agent 当场改写对应规则文件：修正约束、例子与验收；未记录入口先实际执行观察行为，再新增规则文件并入 INDEX。只有现在时，改后跑 `lint.sh --spec` |
| 以规范为准，改代码 | 加载 spec-revise skill：规则不符归因为实现缺陷，未记录入口归因为需求变更，按其路由处理 |

## 收尾

改规范的部分单独 commit，message 说明是对账修正；改代码的部分由 spec-revise 后续流程各自提交。向用户汇报：核对规则数、不一致数、两种裁决各几项、交给 spec-revise 的项。
