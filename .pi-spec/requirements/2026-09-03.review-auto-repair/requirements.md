# 审查未通过的自动归因与有界返修

## 1. 背景

现行规范中，`review-engineer`、`pre-reviewer` 或 `acceptance-reviewer` 一旦返回未通过，流程就停止并等待用户裁决，不做任何自动处理。这把大量可由测试、实现和既有规则自动解决的技术问题转嫁给用户，也让审查中顺带发现的独立问题只能与当前任务混在一起。问题解决后，审查未通过时主 agent 先归因，纯技术问题在既有授权内自动修复并重审，最多三轮；只有真正的产品取舍才询问用户；审查顺带发现的独立问题变成新的后续任务。

## 2. 目标与非目标

### 非目标

- 不让三个审查角色自己修改文件。
- 不执行没有轮次上限的自动返修。
- 不把返修需要扩大目标、文件范围或验收标准的情况当作技术问题自动处理。
- 不把未回答、忽略或取消的问题写入决策台账。

### 目标

- 三个审查角色报告的非产品决策问题在既有授权范围内自动修复并重审，因纯技术问题询问用户的次数为 0。
- 同一审查门禁的自动返修轮次上限为 3，第 3 轮仍未通过时继续自动返修的次数为 0。
- 审查发现的独立问题并入当前任务返修范围的次数为 0。

## 3. 规范变更

| 规范 | 变更 | 说明 |
|---|---|---|
| review-gates/failure-attribution | 新增 | 三个审查角色返回 FAIL 后由主 agent 归因并记录 |
| review-gates/auto-repair | 新增 | 非产品决策问题在既有授权内自动派修并重审 |
| review-gates/repair-round-limit | 新增 | 同一门禁最多三轮返修，第三轮仍未过即停止 |
| review-gates/product-decision-escalation | 新增 | 只有产品决策问题询问用户，未回答不留痕 |
| review-gates/independent-issue-task | 新增 | 审查发现的独立问题新增任务而非并入返修 |

## 4. 边界与已知坑

- 数据量与并发：同一门禁的返修串行执行，不同任务的返修可并行。
- 失败与重试：每个审查门禁最多 3 轮自动返修；修复派发失败、重审结果非法或证据不足均计入轮次并按未通过处理。
- 用户升级：只有产品决策询问用户；返修需要扩大目标、文件范围或验收标准时同样视为产品决策。
- 上下游约束：归因与修复路径的记录依赖需求级决策台账的追加能力；台账追加失败时不派发修复。
- 已知坑：轮次计数若不跟随具体门禁而是跟随整个任务，会让不同角色的返修互相占用额度；三轮停止是确定性状态转换，不额外写入决策台账。
