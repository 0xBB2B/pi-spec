# 审查未通过的自动归因与有界返修

## 1. 背景

现行规范中，`review-engineer`、`pre-reviewer` 或 `acceptance-reviewer` 一旦返回未通过，流程就停止并等待用户裁决，不做任何自动处理。这把大量可由测试、实现和既有规则自动解决的技术问题转嫁给用户，也让审查中顺带发现的独立问题只能与当前任务混在一起。问题解决后，审查未通过时主 agent 先归因，纯技术问题在既有授权内自动修复并重审，最多三轮；只有真正的产品取舍才询问用户；审查顺带发现的独立问题变成新的后续任务。

## 2. 目标与非目标

### 非目标

- 不让三个审查角色自己修改文件。
- 不执行没有轮次上限的自动返修。
- 不把返修需要扩大目标、文件范围或验收标准的情况当作技术问题自动处理。
- 不把未回答、忽略或取消的问题写入决策台账。

### 目标

- 三个审查角色报告的非产品决策问题在既有授权范围内自动修复并重审，因纯技术问题询问用户的次数为 0。
- 同一审查门禁的自动返修轮次上限为 3，第 3 轮仍未通过时继续自动返修的次数为 0。
- 审查发现的独立问题并入当前任务返修范围的次数为 0。

## 3. 术语

| 术语 | 定义 |
|---|---|
| 自动返修轮次 | 某个审查角色返回未通过后，由主 agent 完成一次归因、修复派发并再次调用原审查角色的完整循环。 |
| 产品决策 | 会改变外部可观察行为、数据、安全、权限、验收标准，或无法从已确认需求与项目惯例唯一推导的选择。 |
| 材料性决定 | 存在合理替代方案、已选定一个方案准备执行，且该选择会改变行为、范围、授权、架构、风险、恢复路径或流程分支的选择。 |
| 独立可验证问题 | 具有一个根因、一个可单独触发和验证的预期结果、一个独立验证结论及一个审查裁决的问题。 |

## 4. 需求

### R-1 三个审查角色统一自动归因

当 `review-engineer`、`pre-reviewer` 或 `acceptance-reviewer` 返回未通过时，系统应在保持该角色只读的前提下，由主 agent 区分产品决策与可自动解决的问题并记录归因结果。

### R-2 非产品问题自动返修

当审查问题不需要产品决策且修复不超出用户已授权的目标、文件范围和验收标准时，系统应自动派发所需的测试与实现修复，并再次调用原审查角色。

### R-3 自动返修最多三轮

如果同一个审查门禁的第 3 轮返修后仍未通过，系统应记录技术阻塞并停止，不得继续返修，也不得把纯技术问题转为用户决策请求。

### R-4 仅产品决策询问用户

当审查问题会改变外部可观察行为、数据、安全、权限或验收标准，或无法从已确认需求与项目惯例唯一推导时，系统应询问用户；只有用户形成选择后，系统才应在修改前记录该决定。

### R-5 审查发现独立问题时新增任务

当审查发现的问题与当前任务的根因和预期结果可独立验证时，系统应为该问题新增独立后续任务，不得把它并入当前任务的自动返修。

## 5. 行为方案

审查角色返回未通过后，主 agent 逐条读取问题并归因：当前改动直接造成且违反当前任务预期结果的问题属于当前任务；不需要产品决策且在已授权范围内可修复的，先在 AI 决策台账记录归因与修复路径，再派发测试或实现修复，随后调用原审查角色重审，同一门禁最多三轮；第 3 轮仍未通过时按固定规则停止并报告技术阻塞。需要产品取舍的问题向用户展示具体选项、适用场景与代价，用户形成选择后先写入用户决策台账再执行修复。与当前任务根因无关且可独立验证的问题，新增一个带独立验证结论的后续任务。

## 6. 边界与已知坑

- 数据量与并发：同一门禁的返修串行执行，不同任务的返修可并行。
- 失败与重试：每个审查门禁最多 3 轮自动返修；修复派发失败、重审结果非法或证据不足均计入轮次并按未通过处理。
- 用户升级：只有产品决策询问用户；返修需要扩大目标、文件范围或验收标准时同样视为产品决策。
- 上下游约束：归因与修复路径的记录依赖需求级决策台账的追加能力；台账追加失败时不派发修复。
- 已知坑：轮次计数若不跟随具体门禁而是跟随整个任务，会让不同角色的返修互相占用额度；三轮停止是确定性状态转换，不额外写入决策台账。

## 7. 验收标准

### AC-1 NO-GO 阻断放行并进入返修  ← R-1, R-2
- 触发: 操作 执行一个存在关键测试遗漏的 TDD 任务
- Given: Red 与 Green 阶段均已完成，但测试未覆盖一条验收标准
- When: `review-engineer` 返回 NO-GO
- Then: 任务没有完成且黑盒验收未启动，系统记录该问题为可自动解决的问题，自动补充测试与必要实现后再次调用 `review-engineer`

### AC-2 TDD 审查问题自动修复  ← R-1, R-2
- 触发: 操作 让 `review-engineer` 报告一个不涉及产品决策的实现或测试问题
- Given: 用户已批准的目标、文件范围和验收标准足以完成修复
- When: 主 agent 完成问题归因
- Then: AI 决策台账先出现归因与修复路径记录，随后系统自动派发修复并由 `review-engineer` 重审，期间没有询问用户

### AC-3 提交前审查问题自动修复  ← R-1, R-2
- 触发: 操作 让 `pre-reviewer` 报告一个不涉及产品决策的阻塞问题
- Given: 问题可在已批准范围内通过测试或实现改动解决
- When: 主 agent 校验审查结果并完成归因
- Then: AI 决策台账先记录决定，系统自动完成修复与必要验证，再调用 `pre-reviewer` 重审，未执行任何未经审查的远端写入

### AC-4 黑盒验收问题自动修复  ← R-1, R-2
- 触发: 操作 让 `acceptance-reviewer` 报告一个由实现偏差造成的验收失败
- Given: 需求与验收标准明确且不需要用户选择
- When: 主 agent 核对验收结果和报告并完成归因
- Then: AI 决策台账先记录决定，系统自动派发修复、完成 TDD 审查并再次调用 `acceptance-reviewer`，期间没有询问用户

### AC-5 产品决策升级用户  ← R-4
- 触发: 操作 让任一审查角色报告一个存在两种不同外部行为取舍的问题
- Given: 已确认需求与项目惯例无法唯一决定采用哪种行为
- When: 主 agent 向用户展示具体选项，但用户忽略或取消问题
- Then: 用户决策台账没有新增记录，相关行为没有修改；当用户随后形成明确选择时，系统在执行前只追加一行完整用户决定

### AC-6 自动返修三轮后停止  ← R-3
- 触发: 操作 让同一审查门禁的非产品问题连续三轮修复后仍未通过
- Given: 每轮修复都由已有授权或必要的材料性 AI 决定覆盖，并由原角色重审
- When: 第 3 轮审查再次返回未通过
- Then: 系统停止继续返修并报告技术阻塞，不向用户询问如何解决纯技术问题，决策台账不增加机械状态记录

### AC-7 审查发现其他问题时新增任务  ← R-5
- 触发: 操作 审查一个只负责公共输入校验的任务时发现一个独立的启动器问题
- Given: 启动器问题不影响当前输入校验任务的预期结果，且可以单独验证
- When: 主 agent 完成问题归因
- Then: 系统为启动器问题新增具有独立验证结论的后续任务，当前任务的自动返修范围仍只包含公共输入校验
