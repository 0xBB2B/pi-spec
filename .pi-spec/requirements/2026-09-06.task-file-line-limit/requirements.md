# 任务文件 200 行计数口径

## 1. 背景

用户在编写和拆分任务时发现“每任务改动不超过 200 行”会被理解为限制代码改动量，而实际意图是限制每份任务文件的长度并排除示例代码。现行规范没有任务文件行数规则，公开指令混用了文件长度与代码改动量，且格式、规划、自检的代码块豁免口径不一致。用户确认按规范缺陷处理。

## 2. 目标与非目标

### 非目标

- 不新增代码改动量、示例代码块长度或成品代码块长度上限。
- 不改变每任务生产文件数量、验收引用数量、任务合并、依赖与并行规则。
- 不新增通用行数解析器或自动校验工具，不重写已有任务文件，不修改无关需求及其未提交内容。

### 目标

- 任务格式说明、规划指令和规划核对要求采用同一计数口径，覆盖 3/3 处公开入口。
- 任务文件 200 行合格、201 行超限的两个边界有明确验收，示例与成品两类代码块的排除行为均被覆盖。
- 公开指令中将 200 行解释为预估或实际代码改动量上限的限制为 0 处。

## 3. 规范变更

| 规范 | 变更 | 说明 |
|---|---|---|
| task-planning/task-file-line-limit | 新增 | 明确 200 行约束任务文件、两类代码块豁免及代码改动量不受限 |

## 4. 边界与已知坑

- 数据量与并发：按单份任务文件独立核对，不把多个任务文件相加；既有并行约束不变。
- 失败与重试：需计数内容超限时报告任务文件超限，由既有规划核对流程处理，不增加新的返修机制。
- 上下游约束：后续实现仅涉及 skills/spec-docs/SKILL.md、agents/planner.md、skills/spec-flow/SKILL.md 的行数表述及必要回归测试；本需求不改变子代理派工边界。
- 验证边界：提示词交付物按明确必需句与禁止句逐条测试，覆盖三个入口的一致性；后续运行相关测试和 bun test tests，不把文本测试解释为已实现自动计数工具。草案阶段只运行规范与台账 lint。
- 已知坑：不能把任务文件 200 行误写成预估改动量；不能只写正文而漏掉 frontmatter、标题与空行；不能只排除成品代码块而漏掉示例代码块及两者围栏；不能通过代码块以外的文本格式免除计数。
