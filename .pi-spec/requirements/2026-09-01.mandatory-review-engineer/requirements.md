# 强制 TDD 审查工程师门禁

## 1. 背景

现行 TDD 流程在测试工程师建立失败测试、实现工程师完成最小实现后，会直接运行验证并进入后续验收，缺少独立的需求闭环审查。审查角色虽然已经存在，但角色名称仍在调整，且流程没有把它设为不可跳过的门禁。问题解决后，每个进入 TDD 的任务都必须经过独立审查，用户能够明确看到需求、测试与实现已经形成闭环后，任务才会完成。

审查门禁发现问题后，如果系统一律停止并等待用户，会把可由测试、实现和既有规则自动解决的技术问题转嫁给用户，也无法审计 AI 在流程中做出的自动选择。完整流程需要在保持三个审查角色只读的前提下自动归因、修复和重审，只把确实影响产品行为、数据、安全或验收的未定决策交给用户，并分别记录 AI 决策与用户决策。

## 2. 目标与非目标

### 非目标

- 不要求不采用 TDD 的极小改动进入三阶段流程。
- 不改变测试工程师只修改测试、实现工程师只修改生产实现、审查工程师只读审查的职责边界。
- 不让 `review-engineer`、`pre-reviewer` 或 `acceptance-reviewer` 直接修改文件。
- 不执行没有轮次上限的自动返修。
- 不记录模型私有思维链、秘密、观察结果、机械执行步骤、固定状态转换、临时想法或与流程裁决无关的原始日志。
- 不为同一已形成决定所授权的每个工具调用重复创建决策记录。
- 不改写历史会话、历史任务或历史运行证据中的旧角色名称。
- 不为已经存在的目标行为故意破坏生产配置或测试来制造失败证据。
- 不要求 planner 的自然语言摘要作为结构化门禁；规划仍以落盘文件及其 lint 结果为准。
- 不把 Agent 结构化报告额外持久化到需求目录；结构化对象只在当前编排链中传递。

### 目标

- 采用 TDD 的任务有且仅有一个固定顺序：测试工程师完成后才能启动实现工程师，实现工程师完成后才能启动审查工程师。
- 审查工程师未明确通过时，进入完成状态或黑盒验收的任务数为 0。
- 有效角色目录与工作流说明中旧审查角色名称的残留数为 0。
- 目标行为在 Test 阶段前已经存在时，系统以可信 Green baseline 继续完成实现复核和独立审查，制造假 Red 的次数为 0。
- 三个 TDD 门禁角色的报告均由 JSON Schema 验证，`pre-reviewer` 与 `acceptance-reviewer` 均由主 agent 直接调用并返回严格 JSON，依赖自然语言首行解析做出流程裁决的次数为 0。
- 每个 TDD 任务均以任务编号和任务标题显示为独立 workflow，并以“测试 / 实现 / 审查”展示阶段，通用角色名作为可见节点标题的次数为 0。
- 三个审查角色发现的非产品决策问题均在既有授权范围内自动修复并重审，单个门禁最多执行 3 轮，因纯技术问题询问用户的次数为 0。
- 所有材料性 AI 自动决定与用户决定在形成后、动作执行前分别形成一行可审计记录，未记录决定触发受保护动作的次数为 0。
- 被忽略、取消或未回答的问题进入决策台账的次数为 0，观察与机械工具调用进入决策台账的次数为 0。
- 当前及未来需求文档不再内嵌决策历史，每个需求包分别包含且仅包含一个 AI 决策事实源和一个用户决策事实源。
- 主 agent 与可写子 Agent 的受保护写操作均经过强制门禁；缺少有效决策许可、许可过期或操作超出许可范围时，实际写入次数为 0。
- 作为可安装包分发时，决策门禁不要求安装 Pi 自身运行环境之外的额外语言运行时。
- planner 产出的每个任务均只对应一个独立可验证问题，包含多个可独立裁决问题的任务数为 0。

## 3. 术语

| 术语 | 定义 |
|---|---|
| 审查工程师 | 以 `review-engineer` 名称提供的只读 TDD Review 角色，核对需求、验收标准、测试与实现的闭环。 |
| GO | 审查工程师确认需求闭环、测试质量和实现质量均达到任务门禁的明确通过结论。 |
| NO-GO | 审查工程师发现需求违规、关键测试遗漏、TDD 违规或证据不足时给出的明确不通过结论。 |
| Green baseline | 测试工程师确认目标行为在测试写入前已经存在，并以通过的行为测试证明该现状，无需制造 Red。 |
| 结构化报告 | 三个 TDD 角色通过 `StructuredOutput` 提交并经 JSON Schema 验证的对象，或两个直接审查角色返回的严格 JSON 对象；两种形式均包含统一 `verdict` 字段及阶段专用证据字段。 |
| 严格 JSON | 直接审查角色的完整返回值可解析为唯一 JSON 对象，且对象前后没有说明文字、Markdown 围栏或其他内容。 |
| 任务 workflow | 单个 TDD 任务对应的独立执行视图，总标题由任务编号和任务标题组成。 |
| 自动返修轮次 | 某个审查角色返回未通过后，由主 agent 完成一次归因、修复派发并再次调用原审查角色的完整循环。 |
| 产品决策 | 会改变外部可观察行为、数据、安全、权限、验收标准，或无法从已确认需求与项目惯例唯一推导的选择。 |
| 材料性决定 | 存在合理替代方案、已选定一个方案准备执行，且该选择会改变行为、范围、授权、架构、风险、恢复路径或流程分支，并非现有规则或已批准计划唯一确定的选择。 |
| AI 决策记录 | AI 对材料性问题归因、修复路径、执行范围或流程分支作出的单行可审计摘要，不包含私有思维链。 |
| 用户决策记录 | 用户主动给出或回答后形成的材料性选择及其影响；未回答、忽略或取消的问题不是决策记录。 |
| 决策台账 | 跟随单个需求保存、分别记录该需求 AI 决定与用户决定的追加式 JSONL 事实源；一项已形成决定恰好占一行。 |
| 决策许可 | 由一条已持久化决定生成的有界执行授权，限定任务、工具、文件范围和有效期，可覆盖该决定下的多次机械动作。 |
| 独立可验证问题 | 具有一个根因、一个可单独触发和验证的预期结果、一个独立验证结论及一个审查裁决的问题；同一行为的成功与失败路径仍属于同一个问题。 |

## 4. 需求

### R-1 固定 TDD 三阶段顺序

当任务采用 TDD 时，系统应依次完成 `test-engineer`、`impl-engineer`、`review-engineer`，且后一个阶段不得在前一个阶段完成前启动。

### R-2 审查通过后方可完成

当 `review-engineer` 返回 GO 时，系统应继续执行任务验证，并仅在验证通过后将任务标记为完成。

### R-3 审查未通过时阻断放行

如果 `review-engineer` 未返回 GO、返回 NO-GO 或无法形成可信结论，系统应阻止任务完成和后续验收，并进入有界的归因与返修流程。

### R-4 统一审查角色名称

系统应仅以 `review-engineer` 名称提供 TDD Review 角色，不再以 `req-reviewer` 或 `requirements-reviewer` 名称提供该角色。

### R-5 迁移未完成的 TDD 任务

当本规则生效时，如果已有 TDD 任务已完成实现但尚未最终接受，系统应先补做 `review-engineer` 审查，再决定是否进入黑盒验收。

### R-6 已存在行为使用 Green baseline

当 `test-engineer` 证明目标行为在测试写入前已经存在时，系统应记录可信 Green baseline，继续由 `impl-engineer` 做无修改复核并由 `review-engineer` 审查，不得要求制造 Red。

### R-7 TDD 门禁报告使用结构化裁决

当系统调用 `test-engineer`、`impl-engineer` 或 `review-engineer` 作为 TDD 流程门禁时，系统应通过 JSON Schema 验证其结构化报告，并仅依据统一的 `verdict: PASS | FAIL` 及阶段专用字段决定后续流程。

### R-8 无有效门禁结果时失败关闭

如果 TDD 门禁 Agent 未提交符合 Schema 的结构化报告，或直接审查角色未返回符合约定的严格 JSON，系统应把该门禁视为 FAIL，不得从自然语言、首行、结论段或 PASS/FAIL 子串推断通过。

### R-9 TDD workflow 使用任务标题

当系统启动一个 TDD 任务时，系统应以该任务的编号和任务标题作为对应 workflow 的完整标题。

### R-10 TDD workflow 展示任务化阶段节点

当 TDD workflow 执行时，系统应依次显示“测试”、“实现”和“审查”三个阶段，并在每个阶段内以该任务当前阶段需要完成的具体工作作为节点标题。

### R-11 提交前审查直接返回 JSON

当系统执行提交前审查时，系统应由主 agent 直接调用 `pre-reviewer`，不得为该审查启动 workflow，并应仅依据符合约定的严格 JSON、审查快照和阶段专用字段决定是否允许远端写入。

### R-12 黑盒验收直接返回 JSON

当系统执行黑盒验收时，系统应由主 agent 直接调用 `acceptance-reviewer`，不得为该验收启动 workflow，并应仅依据符合约定的严格 JSON、逐条验收结果和验收报告的一致性决定是否接受需求。

### R-13 三个审查角色统一自动归因

当 `review-engineer`、`pre-reviewer` 或 `acceptance-reviewer` 返回未通过时，系统应在保持该角色只读的前提下，由主 agent 区分产品决策与可自动解决的问题并记录归因结果。

### R-14 非产品问题自动返修

当审查问题不需要产品决策且修复不超出用户已授权的目标、文件范围和验收标准时，系统应自动派发所需的测试与实现修复，并再次调用原审查角色。

### R-15 自动返修最多三轮

在同一个审查门禁中，系统应最多自动执行 3 轮返修与重审；如果第 3 轮仍未通过，系统应记录技术阻塞并停止，不得把纯技术问题转为用户决策请求。

### R-16 仅产品决策询问用户

当审查问题会改变外部可观察行为、数据、安全、权限或验收标准，或无法从已确认需求与项目惯例唯一推导时，系统应询问用户；只有用户形成选择后，系统才应在修改前记录该决定，未回答、忽略或取消的问题不得写入决策台账。

### R-17 材料性 AI 与用户决定按需求单行记录

当 AI 或用户形成影响某个需求的材料性决定时，系统应在对应动作执行前，向该需求自己的对应决策台账追加恰好一行完整决定；观察、机械执行、固定状态转换、临时想法和未形成选择的问题不得写入。

### R-18 决策记录失败时停止

如果对应决策记录未能成功写入或无法通过 JSONL 格式校验，系统应停止执行该决定关联的修复、放行、远端写入或需求接受动作。

### R-19 需求文档不保存决策历史

当系统创建或修订当前及未来需求文档时，系统应只保存当前有效的黑盒契约，不得在需求文档中保留决策记录章节；中断恢复时应从当前 draft 内容重新识别缺失信息，未回答、忽略或取消的问题不得依靠决策台账恢复。

### R-20 接受后仅决策台账可追加

当需求已被接受后，系统应保持该需求的契约、设计、任务和验收交付物不可修改，并仅允许向该需求已有的两个决策台账追加与该需求相关的新决定，不得重写或删除既有决定。

### R-21 决策许可覆盖机械动作

当一条已记录决定授权同一任务范围内的多个机械执行步骤时，系统应使用一个有界决策许可覆盖这些步骤，不得为每个工具调用重复创建决策记录；目标、工具、文件范围或有效期变化时，原许可应失效。

### R-22 无有效决策许可时阻断写入

当主 agent 或可写子 Agent 尝试修改文件或执行其他受保护动作时，系统应在动作执行前验证关联决定及许可；如果许可缺失、无效、过期或与操作范围不匹配，系统应阻断动作并显示原因。

### R-23 审查者不持有修复写许可

当 `review-engineer`、`pre-reviewer` 或 `acceptance-reviewer` 执行审查时，系统应禁止其修改生产代码、测试、需求或其他交付物；`acceptance-reviewer` 仅可在既有任务许可下写入指定验收报告。审查结果引发的材料性修复决定应由主 agent 记录并为后续 Test/Impl 生成修复许可。

### R-24 现有台账一次性规范化

当本规则首次应用于当前需求时，系统应在严格追加门禁启用前，把现有台账中的所有材料性决定转换为一项决定一行的统一格式，删除纯请求、观察和机械执行记录，并提供迁移映射证明材料性决定零丢失；迁移完成后不得再次整体改写。

### R-25 安装包不依赖额外语言运行时

当系统以可安装包形式提供决策门禁时，系统应仅依赖 Pi 自身已有运行环境，不得要求安装额外语言运行时；缺少非必需外部程序不得影响门禁启动。

### R-26 planner 按独立问题拆分任务

当 planner 拆解已确认需求时，系统应使每个任务只对应一个独立可验证问题，并为该问题提供一个独立验证结论和一个审查裁决。

### R-27 复合任务规划失败关闭

如果一个任务中的任一部分可以与另一部分独立通过、失败、审查或回滚，系统应拒绝该规划结果并要求继续拆分，不得进入执行状态。

### R-28 审查发现独立问题时新增任务

当审查发现的问题与当前任务的根因和预期结果可独立验证时，系统应为该问题新增独立后续任务，不得把它并入当前任务的自动返修。

## 5. 行为方案

用户确认一个 TDD 任务的执行组后，系统为每个任务启动独立 workflow，总标题完整显示任务编号和任务标题；并行任务以多个同级 workflow 同时展示。每个 workflow 内依次显示“测试”、“实现”和“审查”，各阶段节点说明当前任务在该阶段需要完成的具体工作。Test 阶段建立 Red；若目标行为在测试写入前已存在，则记录可信 Green baseline，不制造失败。随后完成 Green 或无修改复核，最后执行只读 Review。三个 TDD 角色继续通过带 JSON Schema 的结构化编排返回对象。

提交前审查和黑盒验收不启动 workflow，由主 agent 直接调用对应角色。两个角色的完整返回值必须是唯一 JSON 对象，顶层统一使用 `phase`、`verdict`、`summary`、`issues` 和 `evidence`，并补充阶段专用字段。主 agent 校验完整对象及其与审查快照或验收报告的一致性，只依据有效 `verdict` 决定后续流程。任何前后文字、Markdown 围栏、解析失败、字段缺失、语义矛盾、快照不一致或报告不一致均按 FAIL 处理；不读取首行、结论段或正文中的 PASS/FAIL 子串。尚未最终接受的既有 TDD 任务同样补做审查。

三个审查角色返回未通过后仍保持只读。主 agent 先把问题归因为可自动解决的问题或产品决策；只有归因或修复路径构成材料性决定时，才在执行下一动作前写入对应决策台账。可自动解决的问题在用户已授权范围内派发测试或实现修复，再调用原角色重审，最多 3 轮；产品问题先询问用户，用户形成选择后再记录并执行。第 3 轮仍失败时按固定规则停止属于确定性状态转换，不额外记录为决定。任何必需决策记录失败都阻断相关动作。

每个需求包包含各自独立的 AI 决策台账和用户决策台账，均采用追加式 JSONL 记录，不与其他需求混写。每项材料性决定恰好一行；未回答、忽略或取消的问题、测试输出、Reviewer verdict、机械步骤和工具调用不写入台账。当前需求现有记录在门禁启用前一次性筛选和规范化，保留所有材料性决定并输出迁移映射，随后不再整体改写。需求文档只保留最终有效契约；draft 中断后从当前内容重新识别缺失信息。需求被接受后，契约、设计、任务和验收交付物保持不可修改，后续材料性决定继续只追加到该需求的两个台账。

一条已持久化决定可生成限定任务、工具、文件和有效期的决策许可。许可范围内的多次机械写入不产生额外决策行；范围变化或新材料性选择使原许可失效。主 agent 和可写子 Agent 的受保护动作在执行前经过强制校验，三个 reviewer 始终不持有写许可。

planner 先把需求分解为独立问题，再为每个问题生成一个任务。任务只围绕一个根因和一个独立结果，可以同时覆盖该结果的成功与失败路径。规划完成后，系统检查是否存在能够分别通过、失败、审查或回滚的子问题；存在时退回 planner 继续拆分。审查阶段发现新的独立问题时，系统为其建立新的后续任务，当前任务的自动返修只处理原问题。

## 6. 边界与已知坑

- 数据量与并发：不同且文件互不冲突的任务仍可并发，并以多个同级 workflow 展示；每个任务内部的三个阶段必须严格串行。
- 失败与重试：审查未通过后只对不需要产品决策且不扩大既有授权范围的问题自动返修，每个审查门禁最多 3 轮；第 3 轮仍失败时记录技术阻塞并停止。目标行为已存在不属于失败，但必须有测试工程师记录的可信 Green baseline。TDD 结构化报告缺失、Schema 校验失败、直接审查结果不是严格 JSON或任一结果语义矛盾时均失败关闭。
- 用户升级：内部实现、测试、格式和证据补充由 AI 自动处理；只有存在合理替代方案且会影响外部行为、数据、安全、权限、验收或授权范围的材料性选择必须由用户决定。返修需要扩大目标、文件范围或验收标准时同样视为用户决定。
- 决策记录：每个需求拥有彼此独立的 AI 与用户台账，并只记录本需求的材料性决定；每条记录不得包含秘密或私有思维链。决定必须先成功记录再执行，记录失败不得以全局台账、会话文本或任务备注替代。
- 非决策数据：测试输出、Review 结果、任务状态、工具选择和固定恢复步骤进入各自证据或状态载体，不进入决策台账；只有结果引发新的材料性选择时才追加决定。
- 强制边界：门禁只能约束由当前 agent 运行环境发起的受保护工具调用，无法拦截运行环境之外的进程写入；任何可写子 Agent 必须加载同一门禁，reviewer 不加载写许可。
- 接受后边界：需求被接受后，两个决策台账仅允许追加相关材料性决定；需求契约、设计、任务、验收交付物及既有台账决定均不可修改。
- 上下游约束：角色目录刷新后新名称才可被当前交互会话发现，刷新前不得使用旧名称绕过门禁。TDD 三阶段依赖支持 `agent(..., { schema })` 的 workflow 编排；两个直接审查角色不使用 workflow，必须返回可由主 agent 完整校验的严格 JSON。
- 任务粒度：一个任务只能有一个独立可验证问题；同一行为的成功与失败路径不强制拆开。仅因为多个问题触碰相邻范围、共享验证环境或属于同一需求，不得将它们合并。
- 审查分流：当前任务的自动返修只处理原根因；审查发现的其他独立问题进入新任务。当前改动直接造成且违反当前任务预期结果的问题仍属于当前任务。
- 已知坑：仅修改角色说明而不修改任务步骤状态、自动返修编排和完成门禁，仍会让流程跳过审查或反复询问用户；必须同时约束归因、轮次、决策记录、断点续接和完成条件。直接审查结果虽然使用 JSON，但没有工具层 Schema 保证，因此完整返回值解析或字段校验失败时必须拒绝。结构化对象不落盘时，会话中断且无法恢复 TDD workflow 结果的阶段必须重新执行。

## 7. 验收标准

### AC-1 严格执行三阶段  ← R-1
- 触发: 操作 执行一个需要修改可观察行为的 TDD 任务
- Given: 任务已确认并处于可执行状态
- When: 用户启动该任务的实施流程
- Then: 界面依次显示 `test-engineer` 完成、`impl-engineer` 完成、`review-engineer` 完成，且不存在阶段重叠或跳过

### AC-2 GO 后完成任务  ← R-2
- 触发: 操作 执行一个审查结论为 GO 的 TDD 任务
- Given: Red 与 Green 阶段均已完成，审查所需证据齐全
- When: `review-engineer` 返回 GO
- Then: 系统运行任务验证，并仅在验证通过后把任务标记为完成

### AC-3 NO-GO 阻断放行并进入返修  ← R-3, R-13, R-14
- 触发: 操作 执行一个存在关键测试遗漏的 TDD 任务
- Given: Red 与 Green 阶段均已完成，但测试未覆盖一条验收标准
- When: `review-engineer` 返回 NO-GO
- Then: 任务没有完成且黑盒验收未启动，系统记录该问题为可自动解决的问题，自动补充测试与必要实现后再次调用 `review-engineer`

### AC-4 仅保留新角色名称  ← R-4
- 触发: 操作 刷新角色目录并查看可用 TDD 角色
- Given: 新规则已安装且角色目录已刷新
- When: 用户查看或调用 TDD Review 角色
- Then: `review-engineer` 可用，`req-reviewer` 与 `requirements-reviewer` 均不可用

### AC-5 既有任务补做审查  ← R-5
- 触发: 操作 在新规则生效后恢复一个已完成 Green、尚未最终接受的 TDD 任务
- Given: 任务已有通过的实现与测试证据，但没有审查工程师结论
- When: 用户恢复该任务
- Then: 系统先启动 `review-engineer`，未取得 GO 前不进入黑盒验收

### AC-6 已存在行为不制造 Red  ← R-6
- 触发: 操作 执行一个目标行为在测试写入前已经存在的 TDD 任务
- Given: 测试工程师新增或确认的行为测试首次运行即通过，并证明命中了真实生产路径
- When: 测试工程师报告可信 Green baseline
- Then: 系统继续派遣 `impl-engineer` 做无修改复核，再派遣 `review-engineer` 审查，且没有故意破坏生产配置或测试来制造失败

### AC-7 TDD 三阶段结构化交接  ← R-7
- 触发: 操作 执行一个采用 TDD 的行为改动任务
- Given: 三个 TDD 角色均由带 JSON Schema 的 workflow 调用
- When: `test-engineer`、`impl-engineer`、`review-engineer` 依次完成
- Then: 每个阶段均返回通过 Schema 验证的对象，顶层 `verdict` 仅为 PASS 或 FAIL，且下一阶段只在前一阶段有效 PASS 后启动

### AC-8 验收与提交前审查直接 JSON 裁决  ← R-11, R-12
- 触发: 操作 执行需求黑盒验收或提交前只读审查
- Given: `acceptance-reviewer` 或 `pre-reviewer` 作为流程门禁被主 agent 直接调用
- When: 对应 Agent 完成审查并返回符合约定的严格 JSON
- Then: 界面没有为该审查显示 workflow，系统仅依据有效 `verdict`、阶段专用字段及外部证据一致性决定接受、提交或阻断

### AC-9 非法门禁结果失败关闭  ← R-8
- 触发: 操作 让 TDD 门禁返回非法结构化对象，或让直接审查角色返回前后带说明文字、Markdown 围栏、字段缺失、字段矛盾或无法解析的结果
- Given: 门禁流程正在等待 Agent 裁决
- When: Agent 调用结束
- Then: 系统把结果记为 FAIL，停止后续阶段，并显示结果缺失、解析失败或校验失败的原因

### AC-10 TDD workflow 使用完整任务标题  ← R-9
- 触发: 操作 启动任务 `T-1 统一只读审查工程师角色` 的 TDD 流程
- Given: 任务已确认并处于可执行状态
- When: 系统创建该任务的 workflow
- Then: workflow 总标题精确显示 `T-1 统一只读审查工程师角色`

### AC-11 TDD workflow 展示任务化节点  ← R-10
- 触发: 操作 执行任务 `T-1 统一只读审查工程师角色` 的 TDD workflow
- Given: 该任务依次进入测试、实现和审查阶段
- When: 用户查看 workflow 进度
- Then: 三个阶段依次显示为“测试”、“实现”和“审查”，阶段内节点依次描述验证审查角色名称与只读边界、统一审查角色名称并落实只读职责、核对角色统一与回归证据，不以通用角色名作为节点标题

### AC-12 并行任务显示为独立 workflow  ← R-9, R-10
- 触发: 操作 并行启动两个文件互不冲突的 TDD 任务
- Given: 两个任务分别具有不同的任务编号和任务标题
- When: 两个任务同时执行
- Then: 界面显示两个同级且标题各自完整的 workflow，每个 workflow 内独立显示“测试 / 实现 / 审查”进度

### AC-13 TDD 审查问题自动修复  ← R-13, R-14
- 触发: 操作 让 `review-engineer` 报告一个不涉及产品决策的实现或测试问题
- Given: 用户已批准的目标、文件范围和验收标准足以完成修复
- When: 主 agent 完成问题归因
- Then: AI 决策台账先出现归因与修复路径记录，随后系统自动派发修复并由 `review-engineer` 重审，期间没有询问用户

### AC-14 提交前审查问题自动修复  ← R-13, R-14
- 触发: 操作 让 `pre-reviewer` 报告一个不涉及产品决策的阻塞问题
- Given: 问题可在已批准范围内通过测试或实现改动解决
- When: 主 agent 校验严格 JSON 结果并完成归因
- Then: AI 决策台账先记录决定，系统自动完成修复与必要验证，再直接调用 `pre-reviewer` 重审，未执行任何未经审查的远端写入

### AC-15 黑盒验收问题自动修复  ← R-13, R-14
- 触发: 操作 让 `acceptance-reviewer` 报告一个由实现偏差造成的验收失败
- Given: 需求与验收标准明确且不需要用户选择
- When: 主 agent 核对验收结果和报告并完成归因
- Then: AI 决策台账先记录决定，系统自动派发修复、完成 TDD 审查并再次直接调用 `acceptance-reviewer`，期间没有询问用户

### AC-16 产品决策升级用户  ← R-16
- 触发: 操作 让任一审查角色报告一个存在两种不同外部行为取舍的问题
- Given: 已确认需求与项目惯例无法唯一决定采用哪种行为
- When: 主 agent 向用户展示具体选项，但用户忽略或取消问题
- Then: 用户决策台账没有新增记录，相关行为没有修改；当用户随后形成明确选择时，系统在执行前只追加一行完整用户决定

### AC-17 自动返修三轮后停止  ← R-15
- 触发: 操作 让同一审查门禁的非产品问题连续三轮修复后仍未通过
- Given: 每轮修复都由已有授权或必要的材料性 AI 决定覆盖，并由原角色重审
- When: 第 3 轮审查再次返回未通过
- Then: 系统按固定规则停止继续返修且不向用户询问如何解决纯技术问题；如果停止动作没有新的可选择分支，决策台账不增加机械状态记录

### AC-18 AI 与用户材料性决定按需求分开留痕  ← R-17
- 触发: 操作 在同一需求中先形成一次材料性 AI 修复决定，再完成一次用户产品决定，并在同一许可下执行多次文件写入
- Given: 该需求自己的两个决策台账均可写且格式有效，另一个需求也有自己的台账
- When: 两个决定各自触发后续动作
- Then: AI 决定只在本需求 AI 台账新增一行，用户决定只在本需求用户台账新增一行，另一个需求台账没有新增；同一许可下的多次机械写入没有产生额外决策行

### AC-19 决策记录失败阻断动作  ← R-18
- 触发: 操作 在 AI 即将自动修复或用户决定即将生效前使对应决策台账不可写或产生非法记录
- Given: 相关修复、放行、远端写入或需求接受动作尚未执行
- When: 系统尝试记录决定
- Then: 系统显示决策记录失败并停止，相关动作均未执行

### AC-20 需求文档不再内嵌决策记录  ← R-19
- 触发: 操作 创建一个新需求、提出一个未回答问题并中断会话
- Given: 需求仍处于 draft，用户没有形成选择
- When: 系统恢复该需求
- Then: 需求文档没有决策记录章节，用户台账没有该未回答问题，系统从当前 draft 内容重新识别缺失信息并重新澄清

### AC-21 当前需求迁移且历史不改写  ← R-17, R-19
- 触发: 操作 将当前进行中的需求从全局混合决策记录切换到按需求记录
- Given: 当前全局记录中只有本需求的决定，且存在历史已接受需求与历史会话
- When: 系统完成迁移
- Then: 当前需求已有决定分别进入当前需求自己的两个台账，全局混合台账被删除，需求文档不再包含决策记录章节，历史已接受需求和历史会话内容保持不变

### AC-22 接受后追加提交前决定  ← R-20
- 触发: 操作 对一个已接受需求执行提交前审查并形成新的材料性 AI 自动决定
- Given: 该需求的契约、设计、任务、验收交付物和两个决策台账均已存在
- When: 系统记录并执行该提交前决定
- Then: 一行新决定只追加到该需求的 AI 决策台账；契约、设计、任务、验收交付物、用户决策台账和 AI 台账既有行均保持不变

### AC-23 同一决定不重复记录机械写入  ← R-21
- 触发: 操作 用户批准一个包含 5 个文件修改和 3 条验证命令的任务
- Given: 一条用户授权决定已成功记录并生成覆盖该任务文件与工具的有效许可
- When: Agent 按计划完成全部修改和验证
- Then: 用户决策台账只增加授权决定一行，AI 决策台账没有因机械工具调用增加记录，全部许可范围内动作正常执行

### AC-24 无许可和越界操作被强制阻断  ← R-22
- 触发: 操作 依次尝试一次没有决策许可的文件修改，以及一次使用有效许可但目标文件超出范围的修改
- Given: 受保护动作尚未产生文件副作用
- When: 主 agent 发起两次操作
- Then: 两次操作都在执行前被阻断并显示缺少许可或范围不匹配，目标文件内容保持不变

### AC-25 子 Agent 和 reviewer 同样受门禁保护  ← R-22, R-23
- 触发: 操作 让 Test 或 Impl 子 Agent 在没有有效许可时修改文件，让 `review-engineer` 或 `pre-reviewer` 尝试修改文件，并让 `acceptance-reviewer` 写指定报告后再尝试修改生产文件
- Given: 各角色已按职责加载，验收任务已有仅覆盖指定报告的许可
- When: Agent 发起对应写操作
- Then: Test/Impl 的无许可写入被阻断，两个只读 reviewer 的修改失败，`acceptance-reviewer` 只能写指定报告且生产文件修改失败；主 agent 可在记录材料性修复决定后为后续 Test/Impl 生成有界许可

### AC-26 用户主动决定与 AI 自主决定各占一行  ← R-17
- 触发: 操作 用户在聊天中主动给出一个材料性决定，随后 AI 自主选择一个材料性修复路径
- Given: 两个决定都足以直接控制后续动作
- When: 系统准备执行对应动作
- Then: 用户台账和 AI 台账各新增一行完整决定；记录不包含 pending/resolved 配对、未回答问题、工具调用或执行结果

### AC-27 现有台账规范化且材料性决定零丢失  ← R-24
- 触发: 操作 对当前需求的混合格式台账执行首次规范化
- Given: 台账中同时存在材料性决定、纯请求、观察、机械调度和被后续决定替换的记录
- When: 系统完成迁移并输出逐条映射
- Then: 每项材料性决定在新台账中恰好一行，纯请求、观察和机械记录被删除，被替换关系由新决定单向引用，迁移映射证明材料性决定零丢失，后续整体改写被禁止

### AC-28 无额外语言运行时也能启动门禁  ← R-25
- 触发: 操作 在仅具备 Pi 自身运行环境的全新环境中安装并启动本包
- Given: 环境没有安装任何非必需的额外语言运行时
- When: 系统加载决策门禁并执行 readiness 检查
- Then: 门禁成功进入 ready 状态，受保护工具可按有效决策许可运行，界面没有显示缺少额外语言运行时

### AC-29 复合能力被拆成独立任务  ← R-26
- 触发: 操作 规划一个同时包含公共输入校验、许可存储、受保护写入、验证执行、两类启动器和安装检查的需求
- Given: 各能力可以分别通过、失败、审查和回滚
- When: planner 生成任务清单
- Then: 每项能力分别对应一个具有独立验证结论和审查裁决的任务，任务清单中没有同时交付两个独立能力的任务

### AC-30 复合任务阻断规划完成  ← R-27
- 触发: 操作 让 planner 生成一个同时包含许可存储和启动器接入的任务
- Given: 两部分具有不同根因且任一部分可以独立失败
- When: 系统检查 planner 产物
- Then: 规划结果被拒绝且需求没有进入执行状态，界面显示该任务需要继续拆分的两个独立问题

### AC-31 审查发现其他问题时新增任务  ← R-28
- 触发: 操作 审查一个只负责公共输入校验的任务时发现一个独立的启动器问题
- Given: 启动器问题不影响当前输入校验任务的预期结果，且可以单独验证
- When: 主 agent 完成问题归因
- Then: 系统为启动器问题新增具有独立验证结论的后续任务，当前任务的自动返修范围仍只包含公共输入校验
